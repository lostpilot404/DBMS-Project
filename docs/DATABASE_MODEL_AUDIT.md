# Database model audit — static assessment

Baseline `5db998c9c2205baee51e3718bd724a7a3aba28a2`; no Oracle metadata or DDL execution was available. The absent `R1.pdf` prevents independent verification of assignment attributes. Below, `!` means NOT NULL, `?` nullable; identity keys and data types refer to `sql/01_create_schema.sql`. Oracle DATE includes a time; the UI/API usually supplies midnight, so an actual admission/discharge time is not captured. VARCHAR2 byte/character semantics depend on database configuration; Python length validation is not proof it fits Oracle byte limits.

| Table | Column-by-column assessment and relationships |
|---|---|
| Department | `department_id NUMBER(10)` identity PK; `department_name VARCHAR2(100)!` unique but case-sensitive, allows semantic duplicates; `location VARCHAR2(150)!` is a free-text location, not a location entity. Required location may be unnecessarily restrictive; requirement unavailable. |
| Doctor | `doctor_id NUMBER(10)` PK; `doctor_name VARCHAR2(150)!` single unstructured name; `specialization VARCHAR2(120)!` free text; `phone VARCHAR2(20)?` and `email VARCHAR2(254)?` unique but not normalized; `department_id NUMBER(10)!` FK. No professional registration or inactive state; department changes change historical reports' department. |
| Patient | `patient_id NUMBER(10)` PK is stable, not a separate MRN; `patient_name VARCHAR2(150)!` single field; `date_of_birth DATE!` future check only in API; `gender CHAR(1)!` M/F/O restricts representation; `phone VARCHAR2(20)?` unique prevents household sharing and does not prevent duplicate people; `address VARCHAR2(300)?` and `blood_group VARCHAR2(3)?` constrained. No emergency contact, registration state, allergies or history. Clinical fields should not be inferred or added without defined workflows. |
| Appointment | `appointment_id NUMBER(10)` PK, `patient_id` and `doctor_id NUMBER(10)!` FKs; `appointment_date DATE!` day-truncated; `appointment_time VARCHAR2(5)!` HH:MM check; `status VARCHAR2(20)!` lifecycle; `active_doctor_id`, `active_patient_id NUMBER(10)`, `active_slot_date DATE`, `active_slot_time VARCHAR2(5)` virtual keys enforce exact active slots, not duration overlaps. Trigger guards date/transitions but simultaneous booking/status changes can bypass API's separate-step rule via direct SQL. No encounter, arrival time, clinic hours or duration. |
| Room | `room_id NUMBER(10)` PK; `room_number VARCHAR2(20)!` unique; `room_type VARCHAR2(40)!` free text; `availability_status VARCHAR2(20)!` Available/Occupied/Maintenance. One active admission per room regardless of type; no bed/capacity. Status duplicates admission state; direct Room DML can make it inconsistent. |
| Admission | `admission_id NUMBER(10)` PK; `patient_id`, `room_id NUMBER(10)!` FKs; `admission_date DATE!` SYSDATE default; `discharge_date DATE?` check >= admission; virtual `active_room_id`, `active_patient_id NUMBER(10)` unique. Transfer overwrites room_id, losing earlier room and dates. No separate attending doctor or transfer history. Direct SQL can insert already discharged records, rewrite/reopen history or change patient; room status sync is partial. API now rejects creating discharged admissions. |
| Medicine | `medicine_id NUMBER(10)` PK; `medicine_name VARCHAR2(150)!`, `manufacturer VARCHAR2(150)?`; `price NUMBER(10,2)!` and `stock_quantity NUMBER(10)!` default zero and nonnegative. No unique product identity, strength/form/unit as structured attributes, expiry/batch or movement ledger. Manual adjustment is not dispensing. |
| Prescription | `prescription_id NUMBER(10)` PK; `patient_id`, `doctor_id`, `medicine_id NUMBER(10)!` FKs; `dosage VARCHAR2(200)!`, `duration VARCHAR2(100)!`, `prescription_date DATE!` default SYSDATE. One medicine per row; frequency/route/quantity may be embedded in free text, cannot reliably query. No encounter or order/item distinction or dispensing; edits can reassign patient. |
| Bill | `bill_id NUMBER(10)` PK; `patient_id NUMBER(10)!` FK; `bill_date DATE!` SYSDATE default; `consultation_charge`, `room_charge`, `medicine_charge NUMBER(10,2)!` zero defaults and nonnegative checks; `total_amount NUMBER(11,2)` virtual sum; `payment_status VARCHAR2(20)!` Paid/Pending. Sum fits three maximum components; actual Oracle behavior untested. No invoice lines, encounter/admission reference, payment event/date/method/partial balance or immutability; status can be reversed, charges/patient edited. Reports cannot establish revenue actually received. |

## Relationships, normalization and proposals
All nine FKs and default restrictive deletion are declared; historical names are joined from current master values. FK child columns generally lack dedicated indexes: assess Oracle locking/performance before adding indexes. Virtual columns/unique constraints *intend* active uniqueness, but compilation, Oracle null-index semantics and concurrency need live tests. One-column surrogate keys do not prove 3NF. Room status duplicates occupancy; master changes rewrite the apparent historical context; aggregate charge fields cannot represent variable service lines. Verify all proposed functional dependencies with assignment source.

A room-stay/transfer relation is justified to preserve occupancy history; a stock-movement ledger is justified only if tracking receipts/issues/adjustments or dispensing is required; bill lines and payment events are needed for itemized invoices and partial payments; encounter/diagnosis and prescription header/items are justified only if clinical recording or multi-medication orders are required. Users/roles/audit are necessary for safe real-world access, not cosmetic academic additions. Each needs transactions, authorization, migration/backfill, UI and Oracle tests. No speculative tables or migrations were introduced; existing lost transfer or payment history cannot be reconstructed. Direct-database bypasses remain unresolved.
